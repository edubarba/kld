● Rules 3.1, 3.2, 3.4 and 3.5 conflict with each other, and 3.4 also conflicts
  with section 4. I left out 3.3 as you asked.

  Direct conflicts

  1. 3.2 vs 3.5: attachment dedup breaks families.
  - 3.2 suppresses any attachment whose sha256 matches another attachment.
  - 3.5 says a reviewer must see every attachment on an email.
  - Example: emails E1 and E2 are different messages, but both carry the same
    contract.pdf. 3.2 suppresses one copy, so one email loses an attachment.
  - The same happens inside one family. An email with two identical attachments
    loses one of them.
  - Both rules can't hold at once. The usual fix is to make family the unit of
    suppression. A family, including nested attachments, is suppressed only when
    its top-level email is a duplicate. Attachments are then never suppressed
    on their own.

  2. 3.4 vs section 4: batch-wide dedup breaks custodian completeness.
  - 3.4 dedups across the whole batch, so a document held by custodians A and B
    survives under only one of them.
  - Section 4 says each custodian's set must be complete and self-contained.
  - The load file also has a single Custodian column, so the suppressed copy's
    custodian can't be recorded anywhere.
  - Section 4 sits outside section 3, but it undermines 3.4. The spec has to
    choose one of two options:
    - Dedup per custodian, keeping one copy per custodian.
    - Keep batch-wide dedup and add an all-custodians field. That would change
      the fixed CSV columns, which the spec says it can't do.

  Gaps and ambiguities

  3. 3.1 and 3.2 don't cover a loose file whose hash matches an attachment.
  Loose-to-loose and attachment-to-attachment are covered, but
  loose-to-attachment isn't. Because 3.4 says "entire batch", the intent is
  unclear. If the loose file were suppressed in favour of the attachment, it
  would be fine. If the attachment were suppressed, that would fall under
  conflict 1.

  4. No rule says which copy survives.
  - 3.1, 3.2 and 3.6 say duplicates are suppressed but not which copy is kept.
  - This matters for 6.1 (same output regardless of input order).
  - It also matters for which Custodian, FileName and SentDate the load file
    reports.
  - The spec needs a deterministic tie-break, for example lowest docId, or
    earliest date and then docId.

  5. 3.6 vs 3.5: suppression can leave orphans.
  - If a parent is suppressed but its children are kept, their ParentID and
    FamilyID point at documents that aren't in the load file.
  - 3.6 should say suppression is applied to whole families, children included.

  6. Nested attachments. "Family intact" in 3.5 should say explicitly that it
  covers the full parentId chain. For example, an email attached to an email
  that carries a PDF should be kept or dropped as one unit.

  Suggested consistent rule set

  - Loose files are deduped by sha256. Decide separately whether that also
    covers a loose file matching an attachment.
  - Emails are deduped by 3.3, which I didn't review.
  - Attachments are never deduped on their own. They follow their family: a
    family is suppressed only if its top-level email is a duplicate, and then
    all of it is suppressed.
  - A deterministic survivor rule applies everywhere.
  - 3.4 is reconciled with section 4, which is the decision that needs the spec
    owner.

  I can draft the revised wording for section 3 if you'd like.

● Only 3.1 and 3.6 are tested, and only partly. I read DeduperTests.cs and
  mapped each test to the rules, skipping 3.3.

  Coverage by rule

  Rule: 3.1 loose files with the same sha256 are duplicates
  Covered?: Yes, the basic case
  Test / gap: IdenticalLooseDocuments_SecondIsSuppressed checks that A and B
  have
    the same hash, A is kept, B is suppressed and the count is 1.
    DistinctDocuments_AllKept is the negative case.
  ────────────────────────────────────────
  Rule: 3.2 attachments with the same sha256 are duplicates
  Covered?: No
  Test / gap: Every fixture is built with the Loose helper. No test has an
    attachment or a parentId.
  ────────────────────────────────────────
  Rule: 3.4 dedup across the entire batch
  Covered?: Weak
  Test / gap: The duplicates in the 3.1 test have different custodians (c1 and
    c2), so it touches cross-custodian dedup. But there is no multi-family or
    multi-type scenario, and nothing checks the custodian conflict with section
    4.
  ────────────────────────────────────────
  Rule: 3.5 families produced intact
  Covered?: No
  Test / gap: There is no test with an email plus attachments, no nested chain,
    and no check that FamilyID or ParentID stay valid.
  ────────────────────────────────────────
  Rule: 3.6 suppressed duplicates are omitted
  Covered?: Yes
  Test / gap: Assert.Single(result.Rows) plus Suppressed == 1 in the 3.1 test.
  ────────────────────────────────────────
  Rule: 6.1 order independence (outside 3.x)
  Covered?: No
  Test / gap: Nothing shuffles the input. The 3.1 test even asserts that A, the
    first document, is the survivor, which bakes in the input-order dependence.

  Missing cases

  - 3.2: two attachments with the same hash. The expected result depends on the
    3.2 vs 3.5 decision from my first review, so write this test after the spec
    is fixed.
  - 3.5:
    - The same attachment appears in two different emails, and both emails must
      keep it.
    - An email has two identical attachments.
    - An email is attached to an email that carries a PDF, and the whole chain
      is kept or dropped together.
    - A suppressed parent leaves no orphaned children.
  - 3.1 / 3.2 interplay: a loose file with the same hash as an attachment. The
    spec doesn't define this case.
  - 3.4 vs section 4: the same file held by two custodians. The current test
    asserts that only one copy survives. Section 4 says that may be wrong.
  - 3.1 negatives: same name or size but a different hash must not be
    suppressed, and a loose file must not be deduped against an email.
  - Determinism: run the same batch in reversed or shuffled order and assert
    identical rows.

  Notes

  - The one passing duplicate test encodes behaviour the spec questions (the
    first document seen wins, and the other custodian's copy disappears). If the
    spec changes, it will need to change too.
  - Tests that assert 3.5 would fail against the current Deduper.cs, because it
    suppresses attachments individually. They are good candidates for tests that
    drive the fix.

> @src/DedupTool/Rules/AttachmentDeduplicationRule.cs Why to use a dictionary
  for survivorByHash, a HashSet is much simpler, right?
  ⎿  Read src\DedupTool\Rules\AttachmentDeduplicationRule.cs (26 lines)

● A HashSet of hashes can only answer "have I seen this hash before?". That
  gives "first one seen wins", so the survivor would depend on input order. That
  breaks the requirement that the same batch gives the same output in any order
  (6.1). It's also how the original Deduper.cs behaved.

  The dictionary maps each hash to the lowest DocId found so far. That lets one
  pass over the input pick the same survivor in any order.

  A HashSet does work if you sort first, so the lowest DocId is always seen
  first:

  public IReadOnlyList<Document> Run(IReadOnlyList<Document> documents)
  {
      var seen = new HashSet<string>(StringComparer.OrdinalIgnoreCase);
      var survivors = documents
          .Where(d => d.DocType == "attachment")
          .OrderBy(d => d.DocId, StringComparer.Ordinal)
          .Where(d => seen.Add(d.Sha256))
          .ToHashSet();

      return documents.Where(d => d.DocType != "attachment" ||
  survivors.Contains(d)).ToList();
  }

  This is shorter and has no manual comparison. The cost is an O(n log n) sort
  instead of one O(n) pass, which should be fine even at 2 million documents.
